# ArgusGate v0.1 Development Roadmap

| 属性 | 值 |
| --- | --- |
| Version | v0.1 |
| Status | Phase 0 Complete（Phase 1 Pending） |
| Duration | 6–8 周 |
| Suggested pace | 每天 1–2 小时 |
| Design baseline | [`design.md`](./design.md) |

本文把 `design.md` 中定义的 v0.1 范围拆成可执行阶段。路线服从 `design.md`：如果实现需要改变接口、错误语义、并发所有权或版本边界，应先更新 `design.md`，再调整本路线。

## 1. 路线原则

1. 每个阶段都必须形成可运行、可测试的闭环。
2. 按当前阶段创建目录和抽象，不预建未来包。
3. 先完成正确的串行行为，再引入共享并发状态。
4. SSE、取消传播和 race test 是核心，不为展示性功能让路。
5. 每个任务先明确验收方式，再开始实现。
6. 性能优化必须建立在 benchmark 或 profile 证据上。

## 2. 开工前置条件

Phase 0 开始前需要完成：

- [x] 在实际开发终端执行 `go version`，确认 Go 可直接从 PATH 调用。
- [x] 确定最低 Go 版本并写入 `go.mod`。
- [x] 确定代码托管地址和 Go module path。
- [x] 初始化 Git 仓库。
- [x] 选择首个真实集成后端：优先使用本地更容易运行的 llama.cpp 或 vLLM。

建议把这些选择记录在 Phase 0 的首个提交中，不在 `design.md` 里猜测尚未确定的环境值。

## 3. 里程碑总览

| 阶段 | 时间 | 可演示结果 | Release gate |
| --- | --- | --- | --- |
| Phase 0 | 第 1 周 | 服务可启动、探活、记录日志并优雅退出 | 配置、生命周期和 CI 通过 |

## 4. Phase 0：基础服务

目标：让 ArgusGate 成为一个具备最小配置、日志、HTTP 生命周期和自动检查的 Go 服务。配置只是启动服务的手段，不在本阶段建设通用配置系统。

### 学习重点

- Go module 与 package
- struct、method 与 error
- `net/http`
- `log/slog`
- signal 与 context
- table-driven test

### 任务

- [x] 初始化 `go.mod` 和 `cmd/argusgate/main.go`。
- [x] 只创建 Phase 0 需要的 `internal/app`、`internal/config` 和 `internal/httpapi`。
- [x] 使用 default 提供监听地址，只用 `-config` flag 指定配置文件路径；监听地址由 JSON 覆盖默认值。
- [x] 创建最小 `configs/argusgate.example.json`，只加入当前 Phase 实际使用的字段。
- [x] 实现最小 JSON 加载和必要校验；不做热加载、多环境 profile、复杂覆盖优先级或配置框架。
- [x] 实现 `GET /healthz`。
- [x] 实现 Request ID middleware。
- [x] 实现基础结构化请求日志。
- [x] 定义 `app.Run(ctx, cfg)` 生命周期边界。
- [x] 处理 SIGINT/SIGTERM 和优雅关闭。

- [x] 建立最小 CI：format、vet、test。

### 验收

- 合法配置可以启动服务。
- 文件不存在、JSON 非法和关键字段非法时快速失败，错误可定位。
- `/healthz` 返回 200 和 Request ID。
- 请求结束产生一条不包含敏感信息的结构化日志。
- Ctrl+C 后停止接收请求，并在配置时间内退出。
- `go test ./...`、`go vet ./...` 和格式检查通过。

### 暂不创建

- backend Registry
- Router 接口
- Proxy
- Health Checker
- Prometheus 指标

### Knowledge Checkpoint

进入 Phase 1 前，应能不用照抄代码解释：

- `go.mod`、`package main` 和 `internal/` 分别解决什么问题？
- `http.Handler` 和 `http.HandlerFunc` 是什么关系？
- middleware 如何包装下一个 Handler，为什么顺序会影响行为？
- 为什么错误应在启动边界处理，而不是在底层随意退出进程？
- `Server.Shutdown` 和 `Server.Close` 有什么区别？
- signal、context 和应用生命周期如何连接？

## 5. Phase 1：非流式单后端代理

目标：通过 ArgusGate 调用一个真实 inference backend，完成第一个端到端闭环。

### 学习重点

- `http.Client` 与共享 Transport
- Request/Response 生命周期
- body 一次性读取与重建
- header 过滤
- `httptest.Server`

### 任务

- [ ] Decision gate：确认 model 名原样转发或显式映射；未另行修改 `design.md` 时采用原样转发。
- [ ] 实现 `POST /v1/chat/completions`。
- [ ] 限制并读取原始请求 body。
- [ ] 只解析 `model` 和 `stream`，不重编码 JSON。
- [ ] 校验 backend origin 与 endpoint path。
- [ ] 实现 Phase 1 临时单 backend 直连：只允许恰好一个已通过配置校验的 backend，不读取尚未存在的动态健康状态。
- [ ] 构造使用 handler context 的上游请求。
- [ ] 过滤 hop-by-hop headers，处理 Host、Authorization 和 Request ID。
- [ ] 禁止自动跟随 upstream redirect，透传数据面 3xx。
- [ ] 透传允许的响应 header、状态码和普通响应体。
- [ ] 保证所有路径关闭上游 response body。
- [ ] 实现响应提交前的统一 JSON 错误。
- [ ] 提供仅用于开发和演示的最小 mock backend；在真实 backend 不可用时仍可完成端到端验证。

### 验收

- 可以连接选定的真实 backend 完成一次非流式请求。
- 集成测试证明上游收到原始请求字节和正确 headers。
- 上游 2xx、4xx 和 5xx 状态及响应体正确透传。
- 非法 method、content type、JSON、model 和超大 body 返回设计规定的错误。
- 连接/TLS 失败返回 502，等待响应头超时返回 504。
- 客户端上传超时在可写时返回 408 `request_timeout`。
- response body 在成功、失败和取消路径都被关闭。
- upstream 3xx 不触发第二次请求，Location 指向的服务不会收到 backend credential。

Phase 1 的临时直连只用于建立代理闭环，不是 v0.1 最终路由语义。Phase 3 引入 Registry 后必须删除该分支，由 `model match -> HEALTHY filter -> round-robin` 完整替代；Release Checklist 不允许保留两套选择逻辑。

### Demo Gate

使用两个独立进程完成可见闭环：

```text
curl
  -> ArgusGate :8080
  -> mock backend 或真实 inference backend
  -> JSON response + X-Request-ID
```

Demo 必须记录启动命令、请求命令和预期响应。Phase 1 不为此提前引入 Docker Compose；容器化留到 Phase 5。

### Knowledge Checkpoint

进入 Phase 2 前，应能解释：

- 为什么请求 body 只能消费一次，网关如何在解析后保留原始字节？
- 为什么必须在限制大小之后读取 body，不能无界 `ReadAll`？
- 为什么 `http.Client` 和 Transport 应复用？
- 为什么 `response.Body` 必须在所有路径关闭？
- hop-by-hop header 与 end-to-end header 有什么区别？
- HTTP 响应头写出后，为什么不能再改变状态码？

## 6. Phase 2：SSE 与取消传播

目标：正确处理推理网关最重要的长连接行为。

### 学习重点

- SSE 与 HTTP streaming
- `ResponseWriter`、buffer 与 Flush
- context cancellation
- post-commit error
- goroutine 和资源生命周期

### 任务

- [ ] 以上游 `Content-Type: text/event-stream` 识别 SSE。
- [ ] 检查并保留 ResponseWriter 的 flush 能力。
- [ ] 每次成功写入 SSE chunk 后立即 flush。
- [ ] 记录首次下游 body 写入时间作为 TTFB。
- [ ] 将客户端取消传播到上游。
- [ ] 处理上游 body 读取错误和下游写入错误。
- [ ] 实现 `committed`、实际 status、bytes 与 TTFB 统计口径。
- [ ] 验证优雅关闭宽限期和超时后的强制取消。

### 验收

- 上游立即写首 event 并继续保持 2 秒时，客户端在 500 ms 内读到首 event。
- 客户端取消后，上游 context 在 1 秒内结束；连续执行 50 次均通过。
- 普通响应与 SSE 的 post-commit 错误均能正确分类。
- 强制关闭记录 `shutdown_canceled`，不误记为 `client_canceled`。
- 通过 channel 或 WaitGroup 证明组件拥有的 goroutine 已退出。

Phase 2 可以占用两周。只有“能够看到流式输出”不算完成。

### Knowledge Checkpoint

进入 Phase 3 前，应能解释：

- SSE 与普通 JSON 响应在生命周期上有什么不同？
- 为什么流式响应需要 Flush，哪些包装层可能破坏 Flush？
- 客户端断开后，`request.Context()` 如何让上游请求停止？
- TTFB 和模型 TTFT 为什么不是同一个指标？
- 为什么响应提交后的错误只能终止流并记录？
- goroutine 由谁创建、谁停止、谁等待？

## 7. Phase 3：多后端、路由与健康检查

目标：从单代理演进为并发安全的多后端 inference gateway。

### 学习重点

- goroutine 与 ticker
- `sync.RWMutex` 和 atomic 的边界
- 状态快照
- 并发测试与 race detector

### 任务

- [ ] 实现 Backend 静态配置和动态状态。
- [ ] 实现 Registry 的受控读写和只读快照。
- [ ] 实现 model 精确匹配。
- [ ] 为每个 model 实现独立 round-robin 游标。
- [ ] 正确维护 active requests。
- [ ] 实现 UNKNOWN、HEALTHY、UNHEALTHY 状态机。
- [ ] 实现带 timeout 和并发上限的周期健康检查。
- [ ] 验证健康检查不跟随 redirect，并把所有 3xx 视为失败。
- [ ] 实现 `GET /readyz` 和 DRAINING 状态。
- [ ] 实现健康状态变化日志。

### 验收

- round-robin 顺序可通过确定性单元测试验证。
- UNKNOWN 和 UNHEALTHY backend 不参与路由。
- 达到失败阈值后的下一次选择不返回该 backend。
- 达到成功阈值后的下一次选择可以重新返回该 backend。
- 进入 DRAINING 后 `/readyz` 立即返回 503。
- 100 个客户端各请求 20 次后，`go test -race ./...` 无报告。
- 不在持锁期间执行网络 I/O。

### Knowledge Checkpoint

进入 Phase 4 前，应能解释：

- data race 与业务层面的 race condition 有什么区别？
- `Mutex`、`RWMutex`、atomic 和 channel 各适合什么场景？
- 为什么不能在持锁期间执行健康检查网络请求？
- Router 为什么应读取一次一致快照，而不是边选择边读取共享状态？
- active requests 为什么必须在所有失败路径成对减少？
- `go test -race` 能发现什么，又不能证明什么？

## 8. Phase 4：可观测性

目标：无需阅读代码即可判断请求的路由结果、耗时与失败原因。

### 学习重点

- Prometheus metric types
- label cardinality
- 延迟直方图
- 日志与指标的职责边界

### 任务

- [ ] Decision gate：确认使用 Prometheus 官方 client 或最小文本实现；未另行修改 `design.md` 时采用官方 client。
- [ ] 统一请求结束日志字段。
- [ ] 记录启动、关闭和 backend 状态变化事件。
- [ ] 实现请求总量与延迟指标。
- [ ] 实现 backend health 和 inflight 指标。
- [ ] 实现上游结果、错误与 TTFB 指标。
- [ ] 实现 `GET /metrics`。
- [ ] 检查 labels 不包含 Request ID、原始 URL 或 prompt。

### 验收

- 一条请求结束日志包含 `design.md` 定义的核心字段。
- 可以区分请求错误、路由错误、上游错误、取消和 post-commit 错误。
- backend 健康切换和 inflight 变化可在指标中观察。
- metrics labels 没有高基数或敏感值。
- Grafana 展示是可选项，不阻塞本阶段。

### Knowledge Checkpoint

进入 Phase 5 前，应能解释：

- Counter、Gauge 和 Histogram 分别适合哪些指标？
- 为什么 Request ID 和原始 URL 不应成为 metric label？
- 日志、指标和 tracing 分别回答什么问题？
- 为什么 TTFB 应记录分布，而不只是平均值？
- 如何从日志与指标区分客户端取消、上游超时和强制关闭？

## 9. Phase 5：发布质量与缓冲

目标：把能够运行的代码整理为可复现、可说明、可发布的 v0.1。

### 学习重点

- Docker
- benchmark
- pprof
- README 和 release discipline

### 任务

- [ ] 编写最小多阶段 Dockerfile。
- [ ] 编写 README：定位、架构、启动、配置、调用、测试和限制。
- [ ] 提供本地 backend 联调示例。
- [ ] 编写可复现压测脚本。
- [ ] 记录硬件、Go 版本、backend、模型、命令和原始结果。
- [ ] 检查日志与示例中没有 secret。
- [ ] 完成 v0.1 release checklist。
- [ ] 根据实际瓶颈决定是否记录 CPU/内存 profile；可延后到 v0.1.1。

### 验收

- 新环境能按 README 启动并完成普通与 SSE 请求。
- 本地运行和 Docker 运行行为一致。
- 所有自动测试、race test 和 vet 通过。
- 性能数字可以通过仓库中的说明复现。
- `design.md`、配置示例和实现行为一致。

第 8 周优先作为 Phase 2/3 的风险缓冲。README 美化、Grafana 截图和深入 profile 分析不能挤占核心正确性工作。

### Knowledge Checkpoint

发布 v0.1 前，应能解释：

- benchmark 的环境、输入和比较基线为什么必须记录？
- pprof 数据如何帮助判断 CPU、内存或阻塞瓶颈？
- 为什么“能构建镜像”不等于“容器行为正确”？
- README 中哪些步骤必须由新环境重新验证？
- 哪些能力应进入 v0.2，而不是继续扩大 v0.1？

## 10. 建议提交序列

1. `chore: 初始化 Go 模块`
2. `feat: 加载并校验服务配置`
3. `feat: 增加健康检查接口和结构化日志`
4. `feat: 支持服务优雅关闭`
5. `feat: 代理非流式聊天补全请求`
6. `test: 覆盖上游代理行为`
7. `feat: 实现 SSE 实时转发`
8. `test: 验证客户端取消传播`
9. `feat: 增加后端注册表和轮询路由`
10. `feat: 跟踪后端健康状态和服务就绪状态`
11. `feat: 暴露网关指标`
12. `docs: 增加使用说明、架构和压测报告`

提交可继续细分，但必须保持可运行或可测试。不要把多个无关能力塞进一个提交，也不要单独提交大量尚未使用的空目录和抽象。

## 11. 每个任务的协作闭环

1. **预测**：编码前说明对象拆分、错误传播和验证方式。
2. **实现**：作者先完成最小版本。
3. **评审**：优先指出问题、风险和下一条线索。
4. **修改**：作者根据评审修正，而不是直接替换整份实现。
5. **解释**：结合代码和测试说明设计理由。
6. **记录**：影响系统行为的选择更新 `design.md` 或 ADR。

除非明确要求“直接实现”，默认协作形式是：必要知识、任务说明、验收条件、代码评审、作者修改。

## 12. 版本风险与降级顺序

### 主要风险

- SSE 在代理、middleware 或测试客户端中被意外缓冲。
- 取消信号未传播，导致上游推理继续占用资源。
- Shutdown 与 BaseContext 的关系实现错误，造成无法退出或过早取消。
- Registry 与健康探测出现 data race。
- 过早扩展 OpenAI API 或加入重试、熔断等支线。

### 时间不足时可以延后

1. Grafana dashboard。
2. 深入 pprof 分析。
3. README 视觉美化。
4. 额外 backend 联调。

### 时间不足时不能删除

- SSE 及时 flush。
- 客户端取消传播。
- 上游 response body 释放。
- 多后端健康隔离和恢复。
- race test。
- 最小 README、配置示例和 Docker 运行方式。
